# Decision — live, host-driven mode (2026-08-25)

Supersedes the "New: host view" and "Supabase" sections of
[`../dm-quiz-spec.md`](../dm-quiz-spec.md). Everything else in the spec stands.

## What changed and why

The spec described a self-paced quiz: each player runs the pack alone and the
beamer shows a leaderboard of final scores. Rafa asked for Kahoot instead —
everyone on the same question at the same time, the room's answers visible
after each one, live presence in the lobby, and a running leaderboard.

That is a different shape, not a bigger version of the same one:

- The **host view now owns the game state**. It is a controller, not a display.
- The beamer's end-of-question screen is a **result overview** — how many chose
  each option, with the correct one marked — not just a score table.
- **Presence** is its own thing: the lobby lists everyone who has joined,
  before any score exists.

## Schema

`dm_scores` could not express any of that: it only held a final score, written
once, at the end. It is replaced by three tables — `dm_players`, `dm_answers`,
`dm_state` — in [`../supabase.sql`](../supabase.sql).

All three are **insert-only**. `dm_state` is append-only with the newest row
winning, which means no client ever needs UPDATE, so a participant cannot
rewrite someone else's answer or edit the roster.

## Trust model

Anyone who scanned the QR holds the anon key and can therefore insert a
`dm_state` row and drive the game. That is acceptable for a room of workshop
participants and keeps the client free of any secret. It would not be
acceptable for a public link — that would need state writes behind an edge
function with a host secret.

## Transport: polling, not Realtime

Clients poll every 1.2 s. Supabase Realtime would be lower latency, but it
needs either `supabase-js` (too big to vendor into a single file) or a
hand-rolled Phoenix websocket client. A session is a few dozen phones and a
few hundred rows; polling is comfortably enough and keeps the app
dependency-free.

## Clock

Every device counts down from the host's `started_at`, corrected by the
`Date` response header, so phones with wrong clocks stay in sync. The
countdown paints on `requestAnimationFrame`, which a backgrounded tab or a
locked phone stops delivering — so the visible timer is not authoritative.
`submitAnswer` re-checks the deadline against the server clock and scores a
late tap as no answer.

## Option order

In live mode the shuffle is seeded from the session and question id, so the
beamer and every phone label the same option "A". Otherwise the host says
"most of you picked B" while half the room is looking at a different B. Solo
mode keeps the per-device shuffle.

## Solo mode stays

Spec acceptance 4 — the quiz must be playable when Supabase is unreachable —
is met by falling back to the original self-paced flow, marked 📱 in the UI.
Live mode is the addition, not the replacement.

## Amendment (2026-08-26): rounds and moderation

Two gaps found after the first live run, fixed in
[`../supabase-migration-002.sql`](../supabase-migration-002.sql).

**Rounds.** "New round" did not reset anything. `dm_answers` was unique on
`(session, token, q_index)`, so a returning player's second-round answer
collided with their first, their old score stood, and the leaderboard summed
every round together. Only a player joining under a new name scored at all.
Both `dm_answers` and `dm_state` now carry a `round`, the unique key includes
it, and the host bumps it when starting a new round. A single run-through was
never affected, which is why the first session looked fine.

**Moderation.** Anything typed into the name box is projected to the room and
there was no way to take it down. `dm_kicks` is a new insert-only table: the
host clicks a name in the lobby, a kick row goes in, and every client filters
that token out of the roster, the leaderboard and the answer counts. The
removed player's device stops polling and shows a neutral screen. Nothing is
deleted, so the audit trail survives — and no DELETE grant is needed.

Same trust caveat as driving the game: anyone with the anon key can insert a
kick. Fine in a workshop, not for a public link.
